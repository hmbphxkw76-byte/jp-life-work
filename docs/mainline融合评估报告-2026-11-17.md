## 0. 摘要与结论

**结论：不将 jp-life-work 现有流程整体融合为以 mainline 规范为核心的统一开发流程；采用「双层共存 + 选择性吸收」策略。**

- **报告生产层**（内容交付）保留现有五阶段流程与 AuditGuard 体系，**不改为 11 阶段**——两者核心交付物不同（内容 vs 代码），强融合会造成流程错配。
- **工具链开发层**（代码交付）引入 mainline 的增量能力（规格先行、工单化、TDD、覆盖率门禁、双轴评审、合并前检查单），以一份《工具链开发规约》承载，与报告流程**并行且边界清晰**。
- 现有体系已覆盖 mainline 的全部核心不变量且**更严格**（受保护主线、单一事实源、证据链、隔离合并、失败语义、术语基准、增量验证、状态机），无需重建。

## 2. 现有 CI/CD 全流程梳理

### 2.1 流程环节地图

jp-life-work 存在**两条相对独立的生产线**与**一个周期保障层**：

```
内容生产线（报告交付，月度滚动）
  阶段1 研究核验 → 阶段2 撰写 → 阶段3 审计 → 阶段4 提交合并 → 阶段5 发布
  （PIPELINE-FLOW-SPEC；交付四步协议：preflight → audit_check → submit）

代码生产线（工具链 / 生成物 / 配置）
  任务分支 + worktree → 变更 → unittest → validate → merge（workflow_guard 三层隔离）

周期保障层
  7 条 GitHub Actions：validate / audit-gate / html-sync / scheduled-maintenance /
  info-quality-audit / sampling-repair / （第 7 条定时任务）
```

### 2.2 执行规则

| 规则 | 内容 |
|---|---|
| **退出码契约** | 0=通过；1=阻断（P0/P1）；2=仅 P2/警告放行。CI 显式允许 `{0,2}`，其余非零一律阻断 |
| **双门禁** | `validate.yml`（规范层 L1/L2 + 生成物一致性 + 工作区卫生）+ `audit-gate.yml`（审计层：哈希链 / 登记册 / 已审计标识 / L5 证据） |
| **三层隔离** | ① 分支隔离（`task/<name>` + 独立 worktree）；② 串行合并（全局 merge 锁 + 隔离合并工作树 + `--force-with-lease`）；③ 共享检出锁（checkout 锁） |
| **推送 failover** | `tools/git_push.py`：ssh（`origin`）→ https（`origin-https`），两条都失败即停、不重试 |
| **审计状态机** | `clean / pending / audited / stale`；缺陷路由回源阶段 + 复评闭环 |
| **确定性生成** | HTML 是 md 的确定性派生物；`html-sync` 重生成 + `--check` 校验过期 |
| **左移闸** | `stage_gate_check.py`：闸1 采集 / 闸2 筛选 / 闸3 分类（资产层形态结构检查） |

### 2.3 卡点标准

| 卡点 | 标准 |
|---|---|
| **五闸** | G0 报告骨架（`## 自动验证结果` / `PF-*`）；G1 审计全通过；G2 HTML 与 md 一致；G3 指纹失效即 stale；G4 复核闭环 |
| **多层级校验** | L1 机器可判 → L5 语义复核；P0/P1 阻断、P2 放行 |
| **哈希链** | 台账事件前后哈希相扣，防篡改；登记册 ↔ 台账双向一致 |
| **合并门禁** | 受检报告须 `audited` + 指纹匹配 + 有效 L5 证据，否则退出码 1 |
| **生成物** | `build_hub.py --check` / `md2html.py --check` 防过期 |

### 2.4 治理机制

- **单一事实源**：通用基座模板 `prompt-generic-base.md`；类型模板 `src/report_templates/<类型ID>/`；词库 `src/vocabulary/`；登记册 `*_indicator_registry.md`；工具登记 `registry.json`；CI 文档 `docs/CI.md`。
- **守卫测试**：`test_arch_guard.py`（文档易变数字）、`test_tools.py`、`test_workflow_guard.py`、`test_pipeline_orchestrator.py`、`test_security_regression.py` 等。
- **审计留痕**：台账 + 登记册 + `automation-status.json` 心跳 + 抽检（`audit_sampling.py`）。
- **周期维护**：每月 1 日 00:15 UTC 定时维护（归位/归档/索引/汇总页/失效同步/测试）。
- **编排层（草案）**：`docs/端到端流水线编排系统设计-2026-11-17.md`（S0–S5 六阶段状态机，待审定），只补编排与触发检测，**明确不改动五阶段/五闸**。

## 4. 五维度评估

### 4.1 流程适配性：**低（2.0）**

- 核心交付物不同：mainline 交付「可合并代码」，jp-life-work 交付「研究报告 + 确定性 HTML + 审计证据链」。
- 内容生产阶段（1–2）不可代码化：TDD、覆盖率、红绿重构对「来源分级 / 不虚构」的研究正文不适用。
- 月度滚动节拍与 11 阶段线性模型冲突。
- **结论**：整体适配性低；仅在「工具链开发」子域适配。

### 4.2 落地成本：**整体融合高（2.0）/ 选择性吸收低（4.5）**

| 方案 | 改造成本 | 说明 |
|---|---|---|
| 整体融合 | 20–30 人日 | 需改写五阶段规范、审计状态机、五闸语义、7 条工作流、29 个工具的校验入口、全套文档；且需重定义「内容流程如何映射 11 阶段」 |
| 选择性吸收 | 5–8 人日 | 新增 1 份规约 + coverage 接入 + 1–2 条 CI job + 守卫测试；报告流程零改动 |

### 4.3 团队协作效率：**整体融合低（2.0）/ 选择性吸收高（4.0）**

- 整体融合会让每个内容任务被迫走 11 阶段（研究、写规格、拆工单、TDD…），与「月度核验型只更新登记册」的节拍直接冲突，显著拖慢交付。
- 选择性吸收只作用于工具链变更，内容团队无感知。

### 4.4 质量保障能力：**现有已强（5.0）/ 选择性吸收增益明确（4.5）**

- 现有双门禁 + 审计 L1–L5 + 哈希链 + 抽检已覆盖 mainline 的质量门禁意图，且留痕更强。
- mainline 的增量在**代码侧**：覆盖率与双轴评审能发现契约测试盲区（当前 285 项测试无覆盖率视图）。

### 4.5 长期可维护性：**整体融合低（2.0）/ 选择性吸收高（4.5）**

- 整体融合引入「双轨制」：内容流程与 11 阶段并存 → 规范漂移、文档矛盾、守卫测试复杂化。
- 选择性吸收保持单一事实源，边界由文件范围（`reports/` vs `src/`、`tools/`）天然划分，漂移面小。

## 5. 结论与保留优化方案

### 5.1 核心原因（为什么不整体融合）

1. **交付物异构**：mainline 是代码实现流程，jp-life-work 是「内容 + 代码」双生产线；内容生产线已有更严格的领域专用治理（来源分级、审计哈希链、节拍纪律），不能被通用代码流程替代。
2. **核心不变量已覆盖且更强**：8 条不变量全部有对应实现，其中 5 条（受保护主线、单一事实源、证据链、术语基准、状态机）严格程度超过 mainline。
3. **冲突不可调和**：交付通道（PR vs worktree merge）、节拍模型（线性 vs 滚动）、审计语义（G0 vs 状态机）三处冲突，整体融合必须牺牲其一，代价高于收益。
4. **成本收益倒挂**：整体融合 20–30 人日、收益低且引入双轨漂移；选择性吸收 5–8 人日、收益明确。

### 5.2 现有流程保留方案（不动的部分）

| 保留项 | 说明 |
|---|---|
| 报告生产五阶段 + 交付四步协议 + 五闸 | PIPELINE-FLOW-SPEC 不变 |
| 双门禁 CI（validate + audit-gate） | 语义、退出码契约、`{0,2}` 放行不变 |
| `workflow_guard` 三层隔离 + 双通道 failover | 不变 |
| 审计 L1–L5 + 哈希链 + 抽检 + 状态机 | 不变 |
| `html-sync` / `scheduled-maintenance` / `info-quality-audit` / `sampling-repair` | 不变 |
| 编排器草案（S0–S5） | 继续按原设计推进（它是报告生产的编排层，不是 11 阶段） |

### 5.3 mainline 增量吸收清单（工具链开发域）

| 吸收项 | 落地形式 |
|---|---|
| 规格先行（轻量 to-spec） | 工具链变更 ≥2 文件或新增工具时，先写 ≤1 页规格（动机/接口/验收标准），入 `docs/toolchain/` |
| 工单化 | ≥2 文件变更拆工单（tracer-bullet），登记于任务分支说明 |
| TDD 红绿重构 | 工具链缺陷修复/新功能先写失败测试，再实现；测试入 `src/tests/` |
| 覆盖率门禁 | 接入 `coverage`，统计 `src/prompts-tools/tools/`、`src/vocabulary/script/`、`tools/`；阈值分阶段 60% → 80% |
| 双轴评审 | 工具链变更产出 Standards/Spec 双轴评审报告（沿用现有审查报告形式） |
| 合并前检查单 | 映射 mainline `pr-push-review`：`workflow_guard merge` 前置自检（测试/validate/评审报告/工作区卫生） |

## 6. 落地路线图（分阶段）

### 阶段 P0 · 规约审定（0.5 周）

- 产出《工具链开发规约（TOOLCHAIN-DEV-SPEC v1.0）》：阶段定义、适用范围（仅代码）、命名、异常处理、与内容流程的边界。
- 明确豁免阈值：≤2 文件且无新工具的变更免规格（避免小改动负担）。
- **验收**：用户审定通过。

### 阶段 P1 · 覆盖率基础设施（1 周）

- `requirements.txt` 固定 `coverage` 版本；新增 `.coveragerc`（source 范围限定工具链代码）。
- `validate.yml` 新增 `coverage` job（或并入 unittests job），输出覆盖率报告；阈值先设 **60%（P2 观察，不阻断）**。
- 基线测量并记录当前覆盖率。
- **验收**：CI 可复现覆盖率；基线数值入库（`src/report-audits/toolchain/`）。

### 阶段 P2 · 规格先行 + 工单化试点（1.5 周）

- 在 1–2 个真实工具链任务（如编排器落地、`cleanup` 增强）中实践：规格先行 → 工单 → TDD → 双轴评审。
- 新增守卫测试 `src/tests/test_toolchain_dev_spec.py`：断言规约文件存在、覆盖率阈值配置存在、阶段顺序/边界不变。
- **验收**：试点任务全流程走通；守卫测试通过；既有 285+ 测试无回归。

### 阶段 P3 · 双轴评审 + 合并前检查单 + 阈值提升（1 周）

- 工具链变更 100% 产出双轴评审报告（归档 `docs/toolchain/reviews/`）。
- `workflow_guard merge` 前置检查单（测试/validate/评审报告/工作区卫生）——以文档规约 + 守卫测试固化（不改动 `workflow_guard` 内核语义）。
- 覆盖率阈值提升至 **80%**（阻断）。
- **验收**：评审覆盖 100%；覆盖率 ≥80%；audit-gate 零绕过。

### CI/CD 改造点汇总

| 工作流 | 改造 |
|---|---|
| `validate.yml` | 新增 `coverage` job；阈值读单一事实源配置 |
| `audit-gate.yml` | 可选：工具链变更评审报告存在性（P2 软门禁） |
| 其余 5 条 | **不改造** |
| 守卫测试 | 新增 `test_toolchain_dev_spec.py`；更新 `test_arch_guard.py` 易变数字 |
| 文档 | `docs/CI.md` 增「工具链开发规约」节；`tools/README.md` 增合并前检查单 |

## 7. 风险点与应对

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | 双轨边界模糊，内容任务被强加代码阶段 | 中 | 高 | 规约明示适用文件范围（`src/`、`tools/`）；豁免阈值；守卫测试断言边界 |
| R2 | 覆盖率误伤非工具链脚本（如词库同步） | 中 | 中 | `.coveragerc` source 限定；只统计工具链代码 |
| R3 | 规格先行增加小改动成本 | 中 | 中 | ≤2 文件免规格；模板 ≤1 页 |
| R4 | 与编排器草案重复/漂移 | 中 | 中 | 编排器管报告生产（S0–S5），规约管工具链开发；文档互指 |
| R5 | 覆盖率工具依赖引入环境波动 | 低 | 中 | `requirements.txt` 锁定版本；CI 固定 Python 3.12 |
| R6 | 阈值过早导致 CI 红 | 低 | 中 | 分阶段 60%→80%；先 P2 观察再阻断 |
| R7 | 双轴评审流于形式 | 中 | 中 | 评审报告必须含 Standards/Spec 结论与证据；抽检 |
| R8 | 共享检出目录非本会话改动被误提交 | 低 | 高 | 严格遵守 AGENTS.md「不碰别人的改动」；本次已识别 `findings-by-path.json` 原样保留 |

# 审计报告标准化管理体系（AuditGuard）

> **版本**：v1.9（体系版本 = 下方版本记录末版；登记册 / 已审计标识依据版本为 **v1.4**，与 `audit_registry.SPEC_VERSION` 一致，变更需同步代码与测试）
> **适用范围**：本项目全部业务主题（`00`–`NN`）真实产生的报告（`*/reports/*.md` + 同名 `.html`）
> **上位依据**：[信息质量评估提示词体系](信息质量评估提示词体系.md)（四维度评估与闭环修复，本体系为其**审计化落地**）
> **程序化实现**：`engine/tools/audit_registry.py` / `audit_check.py` / `audit_pipeline.py` / `audit_badge.py` / `audit_sampling.py`
> **设计原则**：全量纳入、标准统一、多级校验、全程留痕、状态可辨、内容防篡改、定期抽检

## 一、总则

### 1.1 目的

把项目内**所有真实业务报告**纳入统一标准管理：使**结构、要素、表述**一致，**信息准确性、来源可追溯性、数据一致性**可校验，「生成 → 初审 → 复核 → 终审」全过程留痕、合规、可追溯，并对通过终审的报告赋予统一、不可伪造的**「已审计」标识**，从源头保障报告信息质量。

### 1.2 与信息质量体系的关系（分层不重复）

| 体系 | 职责 | 产物 |
|---|---|---|
| **信息质量评估与闭环修复**（既有） | 内容**四维度**评估（完整性 / 逻辑一致性 / 信息准确性 / 内容关联性）与自动修复 | 评估台账 / 修复台账 / 验证报告（`engine/report-audits/info-quality/`） |
| **审计标准化管理**（本体系） | 报告**结构 / 要素 / 表述**标准、**多层级校验编排**、**审计流程与留痕**、**已审计标识**、**抽检** | 登记册 / 审计台账 / 审计状态 / 已审计标识 / 抽检报告（`engine/report-audits/audit/`） |

**嵌套关系**：信息质量四维度是本体系**第 2–4 层校验的判定内核**。`audit_check.py` 直接调用 `info_quality_check.evaluate()`，把 C-01～C-16 发现按 `C_TO_LAYER` 映射到审计层级（L2–L5），不重复实现判定逻辑。

### 1.3 术语

- **真实业务报告**：由业务研究流程产出、面向读者交付的报告正文，命名 `YYYY-MM-<主题slug>.md` + 同名 `.html`。插刷件、备份、worktree 副本不算独立报告。
- **内容指纹**：报告 md 源稿字节的 SHA-256（`sha256:<64hex>`）。审计记录与标识均绑定指纹。
- **审计编号**：`AUD-<YYYYMM>-<NNN>`，终审通过时分配，全库唯一。

## 二、管理范畴与登记册

### 2.1 全量纳入

- 登记对象 = `iter_business_dirs()` 遍历到的全部业务主题下 `reports/*.md`。
- 登记册由 `audit_registry.py` **自动发现**，人工不得手工维护；`--check` 校验「登记册 ↔ 实际文件」双向一致（无遗漏、无多余、指纹匹配）。
- 新增主题 / 报告后重新运行 `--init`（幂等：已登记且指纹一致者跳过）即自动纳入。

### 2.2 登记册字段

| 字段 | 说明 |
|---|---|
| `report` | 报告相对路径（`NN-slug/reports/YYYY-MM-slug.md`） |
| `topic` | 主题目录名（`NN-slug`） |
| `topic_slug` | 主题 slug（去 `NN-` 前缀） |
| `period` | 报告期间（`YYYY-MM`） |
| `slug` | 报告 slug（须等于 `topic_slug`） |
| `type_id` | 报告类型（解析自 business-config 的 `report_templates/<类型ID>/` 引用） |
| `content_hash` | md 源稿 SHA-256 |
| `audit_id` | 审计编号（终审通过后填入） |
| `audit_state` | 当前审计状态（见第九节） |
| `finalized_at` | 终审通过时间（ISO8601，未通过为空） |

产物：`engine/report-audits/audit/report-registry.json`（机器可读）+ `report-registry.md`（人读）。

## 三、报告结构 / 要素 / 表述统一标准

报告生成与编排须同时满足**三层基准**，冲突时按「业务配置 ＞ 类型模板 ＞ 通用规范」裁决：

1. **类型骨架**（`engine/report_templates/compliance-rules.json`）：h2 节数与顺序（缺失 = 错误，超额 = 警告并须有业务固化锚声明）。
2. **渲染规范**（`engine/report_templates/monitoring-common-spec.md`）：表格、来源链接、导航、可访问性、打印。
3. **业务固化锚**（各主题 `prompts/business-config.md`）：结构映射表声明的现行结构。

### 3.1 报告必需要素清单（缺一即 L2 不通过）

| # | 要素 | 判定方式 |
|---|---|---|
| E1 | 标题（含期间） | md 首个 `# `；HTML `<title>` 非空 |
| E2 | 版本号 + 数据基准日 | 文首元信息块含「版本」「基准日 / 数据基准」 |
| E3 | 免责声明 | 含「免责声明」或「不构成法律意见」 |
| E4 | 结论摘要 | 含「摘要 / 核心结论 / 结论先行 / 执行摘要」 |
| E5 | 正文（按类型骨架） | h2 节数 ≥ 类型骨架 |
| E6 | 来源章节 | 存在「来源 / 参考来源 / 出处」章节 |
| E7 | 来源标注 | 事实段落来源标注覆盖率 ≥ 20%（程序化门槛，语义目标 100%） |
| E8 | 后续动作 / 观察清单 | 含「观察 / 触发 / 后续 / 待办 / 下期」任一（事件触发型可缺，须声明） |

### 3.2 表述逻辑统一约定

- **推断标注**：凡分析判断标「推断」，算术推导标「自算」，预测标「预测值（F）」；与官方结论分离。
- **口径并列**：不同口径（机构 / 定义 / 周期）**并列呈现，不合并、不取均值**，并注明不可相减 / 不可混用。
- **结论-依据链**：关键结论须具备「事实 → 推理 → 结论」，并附来源。
- **禁止绝对化**：不得出现「必过 / 保证 / 一定 / 100% / 稳过 / 包过」等绝对化措辞（程序化扫描，命中即 L4 提示，语义确认后定级）。
- **断头数字**：报告正文不得出现「有数无源」的关键数字（L3 覆盖率门槛 + 语义复核）。

## 四、多层级信息校验机制

`audit_check.py` 对每份报告执行 L1–L5 五层校验，逐层收敛、逐级留痕。**任一层不通过，不得进入下一审计环节。**

| 层 | 名称 | 校验内容 | 判定来源 |
|---|---|---|---|
| **L1** | 结构层 | 命名合规（`YYYY-MM-<slug>` 且 slug 与目录一致）、md/html 配对、HTML 骨架（h2 节数 / 编号连续 / 锚点）、HTML lint（标签配对 / 列宽 / alt） | `validate.py` + `compliance_check.py` + `lint_reports.py` |
| **L2** | 要素层 | 第 3.1 节 E1–E8 必需要素齐全；主题级必需要素（业务配置 / 登记册 / 操作指南） | `info_quality_check` C-05 / C-06 |
| **L3** | 溯源层 | 来源章节存在性、事实段落来源标注覆盖率、失效引用、URL 形态 | `info_quality_check` C-07 / C-09 |
| **L4** | 一致性层 | 跨文档重复、登记册同名指标口径冲突、报告间数值继承一致、绝对化表述扫描 | `info_quality_check` C-02 / C-03 / C-10 + 扩展规则 |
| **L5** | 语义层 | 结论-依据匹配、表述与来源一致、时效合格、以偏概全、逻辑断层 | 人工 / LLM 复核清单（记录于审计台账） |

### 4.1 层级与严重级别映射

- 每层发现项标注严重级别：**P0**（阻断，必须修复并复评）、**P1**（严重，必须修复）、**P2**（一般，纳入遗留清单）。
- 信息质量四维度发现（C-xx）按性质映射：C-05/C-06 → L2；C-07/C-08/C-14/C-16 → L3；C-02/C-03/C-09/C-10/C-13/C-15 → L4；C-01/C-04/C-11/C-12 → L5（语义确认）。
- **L5 证据门禁**：所有标记 `audited` 的报告必须附带有效 L5 语义复核证据（`re_review --evidence` 或一次性 `--backfill-l5`）；缺失或无效即 `L5-EVIDENCE`，级别 **P1**（阻断），不得进入终审 / 合并。证据须为七项（n21 起新增「独」项）。
- 单层结论：`pass`（无 P0/P1）/ `fail`（存在 P0/P1）；P2 不阻断但须记录。

### 4.2 校验产物

`audit_check.py --all` 输出 `engine/report-audits/audit/audit-check-report.md` + `.json`：逐报告逐层结论、发现明细（层级 / 编号 / 级别 / 位置 / 依据）、全量汇总。

### 4.3 生成后自动验证（AutoVerify 编排层）

`auto_verify.py` 是报告生成后的**无人值守验证入口**，把本节判定内核编排为端到端流程：

| 规则 | 名称 | 复用内核 |
|---|---|---|
| V1 | 交付物与文件可访问 | md/html 存在、可读、非空；命名 slug 与目录一致；html 缺失自动 md2html 补齐 |
| V2 | 必填字段与要素 | `audit_preflight.check_text`（E1–E8 / 命名 / 口径 / 引用 / 登记册指针 / 绝对化） |
| V3 | 格式合规 | `compliance_check` 类型骨架 + `lint_reports` HTML lint |
| V4 | 数据准确性与一致性 | `audit_check`（L3 / L4 + 信息质量四维度，含 C-13 报告↔登记册数值一致性） |
| V5 | 关键指标数值范围 | 登记册活值 ↔ 报告「数据变更摘要」数值覆盖比对 |

流程：验证 → 通过则**幂等写回**报告「## 自动验证结果」章节（仅含数据基准日 / 规则集 / 结论，不含运行时刻，重复验证不产生内容漂移）→ 重新生成 HTML → 写回复核 → 自动 `audit_pipeline --submit`（提交前先撤销过期徽章并失效同步）。失败（任一 P0/P1）→ 退出码 1，打印逐条定位，不写回、不提交。运行日志写入 `engine/report-audits/audit/verify/`（含运行时刻，不入库）。

## 五、审计质量管控流程

### 5.1 环节与状态机

```
registered ──submit──▶ pending_initial ──初审 pass──▶ pending_re_review
     ▲                       │                            │
     │                     初审 fail                      复核 pass
     │                       ▼                            ▼
     │                   rejected ◀──任意环节 fail──  pending_final
     │                       │                            │
     └──修改后重新 submit────┘                      终审 pass
                                                      ▼
                                                  audited ──内容变更（指纹失配）──▶ stale
```

| 环节 | 执行角色 | 进入条件 | 通过条件 | 不通过 |
|---|---|---|---|---|
| 生成 | `generator`（研究 Agent / 人工） | 报告落盘 | L1–L4 自检通过、要素齐全 | 退回修改 |
| 初审 | `reviewer_l1` | 提交（`submit`） | L1–L4 全部 `pass`，P0/P1 = 0 | `rejected`，退回生成 |
| 复核 | `reviewer_l2`（独立于初审） | 初审通过 | L5 语义复核清单逐项确认并附有效证据（缺失即 P1 阻断），L1–L4 无回归 | `rejected`，退回生成 |
| 终审 | `audit_chair`（审计负责人） | 复核通过 | 全环节留痕完整、指纹一致、登记册与状态一致 | `rejected`，退回生成 |

终审通过 → 状态 `audited` → 分配审计编号 → 注入「已审计」标识 → 同步 HTML → 登记册回写。

### 5.2 全程留痕（审计台账）

- 台账文件：`engine/report-audits/audit/audit-ledger.jsonl`，**append-only 事件流**。
- 每条事件字段：`seq` / `ts` / `event` / `report` / `actor` / `role` / `result` / `note` / `content_hash` / `prev_hash` / `hash`。
- **哈希链**：`hash = sha256(prev_hash + 规范化事件体)`，`--verify` 重算全链，任何篡改即断裂。
- 事件类型：`register`（登记 / 重新登记）/ `submit`（提交初审）/ `stage_pass`（环节通过）/ `stage_fail`（环节不通过）/ `revoke`（内容变更撤销）/ `rebind`（渲染漂移重绑）/ `sampling_fail`（抽检不合格失效）。
- 状态派生：`audit-status.json` 由台账派生，含每份报告当前状态、审计编号、终审时间、绑定指纹。
- **幽灵事件清理**：已删除报告（工作树中不存在）的历史事件可经 `audit_pipeline.py --purge-ghosts` 移除，台账 `seq / prev_hash / hash` 重算闭合；真实报告（工作树中存在）的事件、状态与指纹绑定不变。清理后 `--verify` / `--gate --strict` 须通过。

### 5.3 内容防篡改（指纹绑定）

- 每次 `submit` / 环节结论 / 终审均记录当时 `content_hash`。
- `audit_pipeline.py --verify` 比对**当前文件指纹**与终审 `stage_pass`（`role=audit_chair`）绑定指纹：
  - 一致 → `audited` 有效；
  - 不一致 → 标记 `stale`（审计失效），`--sync` 自动写 `revoke` 事件；必须修改后重新走 `submit → 初审 → 复核 → 终审`。
- 「已审计」标识随指纹失效而**自动撤销**（`audit_badge.py --sync`）。

## 六、已审计标识规范

### 6.1 md 源稿标识

通过终审且指纹匹配时，在**文首免责声明块之后**注入统一块（审计编号 / 终审日期 / 指纹 / 依据）：

```markdown
> **已审计** ✅ 审计编号 `AUD-202611-001`｜终审通过：2026-11-14｜内容指纹 `3f8a9c1e2b7d3f8a9c1`｜依据《审计报告标准化管理体系》v1.4
```

- 标识由 `audit_badge.py` 注入 / 撤销，**不得手工添加或修改**。
- 标识含可解析标记 `**已审计**`，供 HTML 渲染与机器校验。

### 6.2 HTML 交付物标识

`md2html.py` 识别上述标记，在报告页 **hero 题头区显著位置**渲染绿色徽章：

```html
<div class="audit-badge" role="status" aria-label="已审计报告">
  <span class="audit-seal">✓ 已审计</span>
  <span class="audit-meta">审计编号 AUD-202611-001 ｜ 终审通过 2026-11-14 ｜ 内容指纹 sha256:3f8a9c1e2b7d ｜ 依据《审计报告标准化管理体系》v1.0</span>
</div>
```

### 6.3 标识与状态一致性

- 仅 `audited` 且指纹匹配的报告允许携带标识；`registered / pending_* / rejected / stale` 一律**无标识**。
- `audit_badge.py --check` 校验「标识存在 ⟺ 状态为 audited 且指纹匹配」，不一致即报 P0。
- 内容变更后标识自动撤销，确保「标识即代表当前内容已通过完整审计」。

## 七、质量验收标准与定期抽检

### 7.1 验收标准（单份报告）

| 维度 | 门槛 |
|---|---|
| L1 结构 | 命名 / 配对 / 骨架 / lint **全部合格**（P0/P1 = 0） |
| L2 要素 | 必需要素覆盖率 = 100%（E1–E8） |
| L3 溯源 | 来源章节存在；事实段落来源标注覆盖率 ≥ 20%；失效引用 = 0 |
| L4 一致性 | 跨文档重复 / 口径冲突 / 断链 = 0；绝对化命中经语义确认后 = 0 |
| L5 语义 | 复核清单逐项确认且**附带有效 L5 证据**（缺失 = P1 阻断）；遗留项仅允许「需人工裁决的事实争议 / 待外部补全」 |
| 流程 | 四环节留痕完整、指纹一致、登记册与状态一致 |

### 7.2 批量验收门槛（抽检口径）

| 指标 | 门槛 |
|---|---|
| 抽检覆盖率 | 每主题至少 1 份，且 ≥ 报告总数的 20%（不足 5 份时全检） |
| 结构合规率 | = 100% |
| 要素完整率 | ≥ 95% |
| 审计状态一致率 | = 100%（标识 ⟺ audited） |
| 抽检合格率 | ≥ 95% |
| P0 / P1 | = 0（任一即整体不通过） |

### 7.3 定期抽检

- 工具：`audit_sampling.py`（分层抽样：按主题分层，逐期轮换，保证每主题在 12 个月内至少被抽中 1 次）。
- 产物：`engine/report-audits/audit/sampling-<YYYY-MM>.md` + `.json`（抽样清单、逐份结论、不合格项、门槛判定）。
- 频率：**每月 1 次**（CI `audit-sampling.yml`，每月 1 日，紧随维护窗口）。
- 不合格处理：命中 P0/P1 → `audit_sampling --apply` 自动写 `sampling_fail` 事件置 `stale`，`audit_badge --sync` 撤销标识，报告重走 `submit → 初审 → 复核 → 终审`；命中 P2 → 纳入遗留清单，下轮复核。

## 八、角色与职责

| 角色 | 标识 | 职责 |
|---|---|---|
| 生成 | `generator` | 按业务配置与提示词产出报告，完成 L1–L4 自检 |
| 初审 | `reviewer_l1` | 独立核查 L1–L4，出具结论与依据 |
| 复核 | `reviewer_l2` | 独立于初审，执行 L5 语义复核清单并抽查 L1–L4 回归 |
| 终审 | `audit_chair` | 审计负责人，确认全环节留痕与指纹一致后签批 |
| 系统 | `system` | 登记、标识注入、状态同步、抽检编排（工具自动执行） |

**独立性要求**：初审与复核不得由同一执行主体完成；终审须由审计负责人签批（初始批次经授权可由 Agent 以 `audit_chair` 身份执行，全程留痕可追责）。

## 九、状态字典

| 状态 | 含义 | 允许的下一动作 |
|---|---|---|
| `registered` | 已登记，未提交 | `submit` |
| `pending_initial` | 待初审 | 初审结论 |
| `in_initial_review` | 初审中（可选中间态） | 初审结论 |
| `pending_re_review` | 待复核 | 复核结论 |
| `in_re_review` | 复核中（可选中间态） | 复核结论 |
| `pending_final` | 待终审 | 终审结论 |
| `in_final_review` | 终审中（可选中间态） | 终审结论 |
| `audited` | 终审通过，标识有效 | 内容变更 → `stale` |
| `rejected` | 某环节不通过 | 修改后 `submit` |
| `stale` | 内容变更，审计失效 | 修改后 `submit` |

## 十、工具与 CI 映射

**合并门禁（`audit_pipeline.py --gate`）** 是 PR / main 推送的统一入口，一次覆盖四类检查：

1. **台账完整性**：重算哈希链，断裂 / 篡改即阻断；
2. **登记册一致**：`audit_registry.check()`（无遗漏 / 无多余 / 指纹匹配）；
3. **标识一致**：`audit_badge` 同口径（audited 必带标识、失效必撤销、md/HTML 一致）；
4. **受检报告审计状态**：默认仅本次变更报告（`--changed <清单>` 或 `git diff base...HEAD`），`--strict` 全库。
   每份须 `audited` + md/HTML 指纹匹配 + 有效 L5 证据；任一不满足即阻断，并打印 `[拦截]` 明细。
   **已删除（工作树中不存在）的报告跳过受检**：门禁校验的是交付物，删除操作不产生待审对象；其台账历史可经 `--purge-ghosts` 清理，未清理前不再阻断合并。

| 工具 | 命令 | 职责 |
|---|---|---|
| `audit_registry.py` | `--init` / `--check` | 登记册生成与一致性校验 |
| `audit_check.py` | `--all` / `--report <path>` / `--json` | L1–L5 多层级校验，输出发现与结论 |
| `audit_pipeline.py` | `--init` / `--submit` / `--review` / `--backfill-l5` / `--status` / `--verify` / `--sync` / `--purge-ghosts` / `--rebind` / `--gate` | 流程状态机与台账留痕；存量 L5 补录；移除台账幽灵事件（重算哈希链）；**合并门禁** |
| `audit_badge.py` | `--apply` / `--revoke` / `--check` / `--sync` | 已审计标识注入 / 撤销 / 校验（含内容漂移更新） |
| `auto_verify.py` | `--report <path>` / `--all` / `--dry-run` / `--no-submit` / `--json` | 生成后自动验证编排（V1–V5）+ 幂等写回 + 自动提交 |
| `audit_sampling.py` | `--apply` / `--report` | 定期分层抽检与门槛判定 |

| CI | 触发 | 内容 |
|---|---|---|
| `audit-gate.yml` | PR / main 推送 | `audit_pipeline --gate`（完整性 + 变更报告审计状态，阻断）+ `audit_check --all`（P0/P1 阻断） |
| `audit-sampling.yml` | 每月 1 日 | `audit_sampling --apply` + 提交抽检报告；不合格告警 |

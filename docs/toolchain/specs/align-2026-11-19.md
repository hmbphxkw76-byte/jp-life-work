# 规格：文档 ↔ 实现对齐与完全对齐验证（align-2026-11-19）

> **任务 slug**：align-2026-11-19（T3 IQ 缓存泄漏 + T8 工具链留痕/守卫）
> **日期**：2026-11-19
> **适用**：TOOLCHAIN-DEV-SPEC S1（≤2 文件且无新增工具，按豁免阈值免 S2 工单化；S5/S6 不豁免）

## 一、动机

- **T3**：`engine/report-audits/info-quality/findings-by-path.json` 是 `audit_check.IQ_CACHE` 运行期写回的可再生缓存，却仍在版本库口径内。跑 `unittest` / `coverage_gate` 会写入它，造成工作区噪声。origin/main 尚未包含忽略条目，需核实并在本分支收口。
- **T8**：`docs/toolchain/specs/` 仅有 `.gitkeep`（无规格留痕）；`tickets/` 有 18 份工单，但 `review_gate` 只断言「评审目录存在至少一份报告」，无法保证「每个工单都有对应评审」。缺一条可执行断言把「文档留痕 ↔ 实现守卫」钉死。

目标：把「文档（specs / tickets / reviews）↔ 实现（工具 / 测试 / CI）」的对齐关系变成可执行守卫，并验证完全对齐。

## 二、接口

| 项 | 内容 |
|---|---|
| 新增规格 | `docs/toolchain/specs/align-2026-11-19.md`（本文件） |
| 新增守卫 | `engine/tests/test_toolchain_dev_spec.py::TestReviewCoverage` |
| 守卫输入 | `docs/toolchain/tickets/*.md` 的 slug 集合；`docs/toolchain/reviews/*.md` 的标题行与「工单」声明行 |
| 守卫判定 | 工单 slug 精确出现在评审标题或工单声明行（`> 工单：` / `> **工单**：`），**或**工单正文显式含「免评审」 |
| 守卫输出 | unittest 断言；缺失即失败（红），`unittest` / `validate` 退出码 0 为通过 |
| 不改项 | `engine/tools/review_gate.py`、`.github/workflows/audit-gate.yml`（软门禁保持，见决策记录） |

## 三、验收标准

1. **T3**：`git check-ignore engine/report-audits/info-quality/findings-by-path.json` 命中；跑 `python -m unittest discover -s engine/tests` 后 `git status --short` 无该文件；origin/main 未含该条目的事实被记录，合并时保留条目。
2. **T8-a**：本规格存在且含「动机 / 接口 / 验收标准」三要素。
3. **T8-b**：18 个工单 slug 全部被评审覆盖或显式标「免评审」；`TestReviewCoverage` 通过；`unittest` 全绿、`validate.py` 退出码 0。覆盖来源限定为评审标题 / `> **工单**：` 行，正文偶然提及工单路径不算覆盖。
4. **S5**：产出双轴评审 `docs/toolchain/reviews/harden-engine-review.md`，Standards / Spec 均无 P0/P1。

## 四、决策记录：`review_gate` 是否转硬门禁

**本轮不改 `.github/workflows/audit-gate.yml`，保持软门禁。** 理由：

- 当前 `review_gate` 粒度是「评审目录存在至少一份报告」，**不是**「本次变更文件 ↔ 对应评审」；直接转硬会因历史工单缺对应评审而阻断 main 推送，误伤面大。
- 本任务新增的守卫测试已把「工单 100% 评审覆盖」变成可执行断言，职责更精准；CI 硬门禁应建立在该守卫稳定之后。
- **触发条件**：守卫测试连续稳定 ≥1 个月，且 `review_gate` 增加「变更文件 ↔ 评审覆盖」粒度后，再评估把 `audit-gate.yml` 的 `|| code=$?` 容忍改为阻断（退出码 1）。
